IDEAS
    Data strutures
        - vector, map, unordered_map, set, unordered_set, deque, queue, priority_queue

        map
            - balanced bst (i.e. red-black tree)
                - ensures logn search/insert/delete
        
        unordered_map
            - general techniques:
                - separate chaining (N buckets, each holds list of kv pairs):
                    - low cache locality -> pointer chasing down list
                    - lookup -> O(1) avg, slower if clustered (walk the list)
                    - insert -> O(1)
                - open addressing (each slot on kv pair):
                    - high cache locality -> just contiguous memory
                    - lookup -> O(1) avg, walking forward faster than walking separate chaining list
                    - insert -> O(1) avg, clustering makes longer

            - linear probing
                - insert at hash, or first free spot in front of it
                - leave tombstones behind so deletion doesn't break the probe chain
            - robin-hood hashing
                - linear probing + consideration of 'probe length'
                - probe forward, insert at:
                    - empty slot OR;
                    - entry with shorter probe length, swap, continue find space for swapped entry
                - key idea: steal from rich, make things equitable
                    - flattens long probe chains so everyone has more equal probe times
            
            - plan:
                - linear probing
                - then robin-hood hashing
                - benchmark against each other

SCRIBBLES
    - unordered_map
        - hash function
            - needs to be able to hash all keys
            - use std::hash of the key
            - power of two bucket size so that:
                - hash % bucket_size <==> hash & (bucket_count - 1)

        - why is hash & (bucket_count - 1):
            - equivalent
                - example
                    - bucket_count == 2^8 == 0001 0000 0000
                    - bucket_count - 1 == 0000 1111 1111
                    - hash == 2^8 + 1 ==> hash & bucket_size = 1
                    - hash = 0001 0000 0001
                    - therefore, hash & (bucket_count - 1):
                         0001 0000 0001
                         0000 1111 1111
                         --------------
                         0000 0000 0001
                - reasoning:
                    - if bucket_size is 2^k, 2^k - 1 is all ones in the range [0, 2^k - 1]
                    - therefore, bitwise anding it with hash just leaves all the quantity
                    of 'hash' in range [0, 2^k - 1], whilst discarding the higher bits...genius!
            - faster
                - not performing costly division, instead doing bitwise &
